# TanStack Query — ข้อมูลจาก server ไม่ใช่ของเรา

ทำไมโปรเจกต์นี้ไม่เก็บรายชื่อ user ด้วย `useState`: เพราะ `useState` ถูกออกแบบมาสำหรับ
ข้อมูลที่ **เราเป็นเจ้าของ** แต่รายชื่อ user เป็นของ server เราถือแค่ **สำเนา** ที่เก่าได้ตลอดเวลา —
ดู `client/src/pages/UsersPage.tsx` และ `client/src/main.tsx`

> คู่กับ [axios](axios.md) ซึ่งแก้ **คนละปัญหา** — axios ไปเอาข้อมูลมา ตัวนี้ดูแลข้อมูลที่เอามาแล้ว

## TL;DR (อ่านทวนเร็ว)

- **แกนเดียวที่ต้องจำ: ข้อมูลจาก server เป็น "สำเนาของคนอื่น" ไม่ใช่ของเรา** — ฟีเจอร์ทุกตัวงอกจากประโยคนี้
- **มันไม่ยิง request เอง** — เราส่งฟังก์ชันที่ยิงให้มัน (จะใช้ `fetch` หรือ `axios` ก็ได้ มันไม่สน)
- **`queryKey` คือ "ที่อยู่" ของข้อมูลใน cache** ไม่ใช่แค่ชื่อ — key เดียวกัน = ข้อมูลชุดเดียวกัน
- **cache อยู่ใน memory** → รอดตอนเปลี่ยนหน้า · **หายตอน refresh / ปิดแท็บ**
- **`staleTime` = เวลาที่ถือว่าข้อมูล *ยังสด*** พ้นแล้วติดป้าย `stale` — **ไม่ใช่เวลาที่ให้เก่า**
- **stale แล้วยังไม่ refetch ทันที** — รอ trigger: component mount ใหม่ · สลับแท็บกลับมา · เน็ตกลับมา
- **ความเก่าวัดจาก "เวลา" ไม่ได้ไปถาม server** — ถ้าต้องถามก็ต้องยิง request อยู่ดี ซึ่งขัดกับเหตุผลที่มันมีอยู่
- **`invalidate` = ข้ามนาฬิกา** บอกตรงๆ ว่าเก่าแล้ว → ตัวที่ Phase 3 ใช้หลังสร้าง user
- ได้ `data` / `isPending` / `error` มาให้ — **ไม่ต้องสร้าง state เอง**

## 1. แกน — ทำไม `useState` ไม่พอ

```
useState      ตั้งอยู่บนสมมติฐานว่า "ข้อมูลนี้เป็นของเรา"
              → เราเปลี่ยนคนเดียว → ไม่มีใครมาแก้ข้างหลัง → ไม่มีวันเก่า

รายชื่อ user   เจ้าของคือ server → เราถือสำเนา
              → admin อีกคนเพิ่ม user ได้ตลอดเวลา → สำเนาเราเก่าได้เสมอ
```

**`useState` ไม่มีแนวคิดเรื่อง "เก่า/ใหม่" เลย** มันรู้แค่ "มีค่า" กับ "ไม่มีค่า"

## 2. ทุกฟีเจอร์คือผลพวงจากประโยคเดียวนั้น

| เพราะเป็น "สำเนาของคนอื่น" | จึงต้องมี |
|---|---|
| สำเนาเดิมยังใช้ได้ ไม่ต้องขอใหม่ทุกครั้ง | **cache** |
| สำเนาอาจเก่า ต้องแอบเช็คเป็นระยะ | **refetch เบื้องหลัง** |
| เราเพิ่งแก้ต้นฉบับเอง สำเนาเก่าแน่นอน | **invalidate** |
| หลายหน้าถือสำเนาเดียวกัน | **แชร์ cache / รวม request** |
| ขอไม่สำเร็จ ลองใหม่ได้ ต้นฉบับไม่เสียหาย | **retry** |

**ไม่ต้องท่อง 5 ข้อนี้** — จำแค่ *"มันเป็นสำเนาของคนอื่น"* แล้วคิดออกเอง

## 3. มันไม่ยิง request เอง

```ts
useQuery({
  queryKey: ["users"],
  queryFn: ({ signal }) => getUsers(signal),   // ← เราเป็นคนเขียนตัวยิง
});
```

**TanStack Query จัดการสิ่งที่เกิดขึ้น *รอบๆ* การยิง ไม่ใช่ตัวการยิง** — `signal` ที่มันส่งมาให้
คือ `AbortController` ที่เราเคยเขียนเอง มันยกเลิกให้เมื่อ component ถูกถอดหรือ query ถูกแทนที่

> ใน dev จะเห็น request แรกขึ้นสีแดงใน DevTools เสมอ — นั่นคือ StrictMode รัน effect 2 รอบ
> แล้วอันแรกถูก abort **ไม่ใช่ error** (ดูจาก: ไม่มี Status Code, Response headers ว่าง)

## 4. `queryKey` — ที่อยู่ของข้อมูลใน cache

```
["users"]          →  cache ช่องรายชื่อ user
["tickets"]        →  คนละช่อง
["tickets", 5]     →  ช่องของ ticket id 5 โดยเฉพาะ
```

**key เดียวกัน = ข้อมูลชุดเดียวกัน** → 2 component ขอพร้อมกัน ยิง request ครั้งเดียว

## 5. cache เก็บที่ไหน

```
เก็บใน memory (RAM) ของหน้าเว็บที่เปิดอยู่   ← ที่นี่
ไม่ใช่ localStorage · ไม่ใช่ไฟล์บนดิสก์
```

| ทำอะไร | cache |
|---|---|
| กดเมนูเปลี่ยนหน้าไปมา | **ยังอยู่** → กลับมาข้อมูลขึ้นทันที |
| กด F5 / ปิดแท็บเปิดใหม่ | **หายหมด** → โหลดใหม่ตั้งแต่ต้น |

cache อยู่ที่ `queryClient` ซึ่งสร้างไว้ **นอก component** และห่อทั้งแอปด้วย
`QueryClientProvider` ใน `main.tsx` — **นั่นคือเหตุผลที่มันรอดตอน component ถูกถอด**
(ถ้าสร้างข้างใน component ทุก re-render จะได้ cache ใหม่เปล่าๆ = ไม่มี cache)

## 6. `staleTime` และ trigger — จุดที่สับสนที่สุด

```
staleTime = เวลาที่ถือว่าข้อมูล "ยังสด (fresh)"     ← ไม่ใช่เวลาที่ให้เก่า
```

**ลำดับที่เกิดขึ้นจริง — ③ แยกจาก ② สนิท**

```
① data มาถึง             →  fresh
② ผ่านไป = staleTime     →  ติดป้าย stale   ← เงียบๆ ไม่มีอะไรเกิดขึ้น
③ มี trigger             →  ถ้าตอนนั้น stale → ค่อย refetch
```

**3 trigger:**
```
① component ที่ใช้ query นี้ mount ใหม่   (กลับเข้าหน้านั้นอีกรอบ)
② สลับแท็บไปแล้วกลับมา                   (window refocus)
③ เน็ตหลุดแล้วกลับมา                     (reconnect)
```

**เปิดหน้าค้างไว้เฉยๆ 10 นาที ไม่มี trigger = ไม่มี request สักครั้ง** ถึง data จะ stale ไปแล้วก็ตาม

### ความเก่าวัดจากนาฬิกา ไม่ได้ถาม server

```
data มาถึงเมื่อไหร่ + staleTime  <=  เวลาตอนนี้   →  stale
```

**เหตุผล: ถ้าจะถาม server ว่าสำเนาเก่าหรือยัง ก็ต้องยิง request อยู่ดี** ซึ่งขัดกับเหตุผลที่มันมีอยู่

```ts
staleTime: 0           // default — stale ทันทีที่ได้มา → ทุก trigger ทำให้ refetch
staleTime: 2 * 60_000  // เชื่อสำเนา 2 นาที
staleTime: Infinity    // ไม่เก่าเอง จนกว่าจะสั่ง invalidate
```

**โปรเจกต์เราใช้ default `0`**

## 7. `invalidate` — ข้ามนาฬิกาทั้งหมด

```ts
queryClient.invalidateQueries({ queryKey: ["users"] });
```

> "ไม่ต้องสนเวลา ฉันรู้ว่ามันเก่าแล้ว **เพราะฉันเพิ่งแก้ต้นฉบับเอง**"

**นี่คือตัวที่ Phase 3 จะใช้** — สร้าง user สำเร็จ → invalidate → ตารางอัปเดตเองโดยไม่ต้องสั่ง refetch

## 8. 3 ค่าที่ได้กลับมา

```ts
const { data: users, isPending, error } = useQuery({ ... });
```

| ค่า | แทนอะไรในโค้ดเดิม |
|---|---|
| `isPending` | `users === null` ที่เราอนุมานเอง |
| `error` | `useState<string \| null>` |
| `data` | `useState<UserRow[] \| null>` |

**3 สถานะนี้ไม่เกิดพร้อมกัน** → render เขียนเรียงกันได้เลย ไม่ต้องซ้อนเงื่อนไข

---

## หลักจำ

> **ข้อมูลจาก server เป็นสำเนา ไม่ใช่ของเรา**
> TanStack Query คือที่เก็บสำเนาที่รู้ว่าตัวเองเก่าหรือยัง — และ "รู้" ด้วยการดูนาฬิกา
> ไม่ใช่ด้วยการถามต้นฉบับ
>
> จำประโยคแรกไว้ประโยคเดียว แล้ว cache / refetch / invalidate / retry คิดออกเอง
