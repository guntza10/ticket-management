# เมื่อไหร่ควรแยก component ออกเป็นไฟล์ใหม่

## กฎทั้งหมด — 2 ประโยคของ React

จาก doc ของ React เอง ไม่ต้องแปล ไม่ต้องตั้งศัพท์ใหม่:

> **"a component should ideally only be concerned with one thing. If it ends up growing,
> it should be decomposed into smaller subcomponents."**

> **"Separate your UI into components, where each component matches one piece of your
> data model."**

สังเกตว่า **ทั้ง 2 ประโยคไม่พูดถึงการ reuse เลย** และตัวอย่างใน doc เขาเอง (`Recipe`
แยกจาก `RecipeList` · `Report` แยกจาก `ReportList`) **มีไฟล์ที่ใช้มันไฟล์เดียวทั้งคู่**

ไฟล์นี้มีแค่ 2 เรื่องที่ต้องเติม: **คำว่า "โต" หมายถึงอะไร** กับ **ช่องที่ React เงียบไว้**

---

## 1. "โต" วัดที่จำนวนเรื่องที่รับผิดชอบ ไม่ใช่ความยาว

2 ประโยคข้างบนเป็นเรื่องเดียวกัน ไม่ใช่ 2 เงื่อนไข — **"growing" คือคำที่ React ใช้เรียก
อาการของการที่ component เริ่มรับผิดชอบเกิน 1 เรื่อง**

ของจริงในโปรเจกต์นี้ที่พิสูจน์ว่าความยาวไม่ใช่ตัววัด:

| | ยาว | รับผิดชอบกี่เรื่อง | ผล |
|---|---|---|---|
| `client/src/features/users/components/EditUserForm.tsx` | 108 บรรทัด | **1** — ฟอร์มแก้ user | **ไม่แยก** |
| `client/src/pages/UsersPage.tsx` (ก่อน 2026-10-26) | 139 บรรทัด | **2** — จัดการ roster ทั้งก้อน **+** ตัดสินว่าแต่ละแถวหน้าตายังไง | **แยก** |

และ `UsersPage` ตรงกับประโยคที่สองด้วย: **1 แถว = 1 user ในตาราง `user`** — ของชิ้นนี้
มีตัวตนอยู่ก่อนที่ใครจะเขียนโค้ด เพราะ database มีแถวนั้น

---

## 2. ช่องที่ React เงียบไว้ — ของที่ไม่ตรงกับข้อมูล

ประโยคที่สองบอกว่า *ตรงกับข้อมูล → แยก* แต่**ไม่ได้บอกว่าของที่ไม่ตรงกับข้อมูลต้องทำยังไง**

> **เติมช่องนี้:** ของที่เราคิดขึ้นเองเพราะเห็น markup คล้ายกัน (ไม่ตรงกับข้อมูลชิ้นไหนเลย)
> → **รอให้มี 2 ไฟล์ที่ `import` มันก่อน ค่อยแยก**
>
> เพราะ **prop ของมันไม่มีใครกำหนด เราเดา** — และคนที่บอกได้ว่าเดาถูกหรือผิด คือไฟล์ที่ 2
> ที่มาใช้

การนับ "2 ไฟล์" นับตรงตัวด้วย `grep` และนับ**ไฟล์ที่เขียน `import`** ไม่ใช่จำนวนครั้งที่ render:

| สิ่งที่เห็น | นับได้ |
|---|---|
| `UsersPage` `map` แล้ว render `UsersTableRow` 3 แถว | **1 ไฟล์** |
| มี `useCreateUser` อยู่ แล้วเขียน `useUpdateUser` ที่หน้าตาคล้ายกัน | **ไฟล์ละ 1** — hook ที่สองที่คล้ายกัน ไม่ใช่คนมาใช้ของเดิม |
| ไฟล์ `*.test.tsx` ที่ import มัน | **ไม่นับ** — ไม่ใช่ส่วนของแอป |

## 3. หลักฐานเคสที่ 1 — `FormField` สร้างแล้วถอนออก (2026-10-20)

ดู `client/src/features/users/components/EditUserForm.tsx` บรรทัด 85-125 — มี 3 ก้อนคล้ายกัน:

```tsx
<Field data-invalid={!!errors.name}>
  <FieldLabel htmlFor="edit-user-name">Name</FieldLabel>
  <Input id="edit-user-name" aria-invalid={!!errors.name} {...register("name")} />
  <FieldError errors={[errors.name]} />
</Field>
```

เห็นซ้ำ 3 รอบ เลยตั้งชื่อว่า `FormField` แล้วย้ายออก — **แต่ "FormField" ไม่ตรงกับข้อมูล
ชิ้นไหนเลย** ไม่มีตารางชื่อนี้ ไม่มี record ชื่อนี้ มันเกิดจากการเห็น markup คล้ายกันเท่านั้น

เพราะงั้น prop ต้องเดา และเดาจาก 3 field ที่เห็น → `{ label, error, children }`

**แค่ 3 field ในฟอร์มเดียวก็ไม่เข้าพิมพ์แล้ว:**

- `name`, `email` — label + input + error ✅ ตรงที่เดา
- `password` (บรรทัด 110-125) — มี `FieldDescription` เพิ่ม **และ** input เป็น `PasswordInput`
  ไม่ใช่ `Input`

วันที่ฟอร์ม ticket มาถึง (dropdown เลือก category, textarea) prop ที่เดาไว้จะไม่พอ → ต้อง
กลับไปแก้ `FormField` → **กระทบทุก field ที่ใช้มันอยู่**

**และเหตุผลที่เป็นตัวตัดสินให้ถอนออกจริงๆ:** ไป query doc ของ shadcn แล้วพบว่า `Field`
เป็น **markup เปล่าๆ** และ **ทุกตัวอย่างในเอกสารต่อ `id` / `htmlFor` / `aria-invalid` ด้วยมือ
ทั้งหมด** → wrapper ที่เขียนไป "เพื่อแก้" ปัญหานี้ คือการแก้ปัญหาที่ library ไม่ได้มี

> **บทเรียน:** ไปอ่านตัวอย่างการใช้งานในเอกสารก่อนสร้างของมาอุด "ช่องว่าง" — รูปร่างที่
> เอกสารเขียนไว้ คือรูปร่างที่ tutorial, ผลค้นหา และตัวเราตอนกลับมาอ่าน doc อีกรอบจะเห็นตรงกัน

## 4. หลักฐานเคสที่ 2 — `UsersTableRow` แยกออกมา (2026-10-26)

**ถูกปฏิเสธมา 2 รอบก่อนหน้านี้** เพราะกฎเวอร์ชันเก่าในโปรเจกต์นี้เรียง "มีไฟล์อื่นเรียกไหม"
ไว้ข้อแรก และเขียนว่า *เจอ no ข้อแรกให้หยุดเลย* → หยุดก่อนที่เกณฑ์อื่นจะได้พูด

**กฎเก่านั้นเหมารวมมาจากเคส `FormField` เคสเดียว** — ซึ่ง `FormField` ตกเกณฑ์นั้นจริง
แต่พอเอามาใช้กับแถวตารางที่ตรงกับข้อมูล มันให้คำตอบผิด และไม่มีใครเคยไปเช็ค 2 ประโยค
ของ React

### ผลตอบแทนที่จับต้องได้คือ test ไม่ใช่จำนวนบรรทัด

**ก่อนแยก** — 3 เงื่อนไขที่แถวตัดสิน (จาง / มีป้าย `Deleted` / มีปุ่มอะไรบ้าง) อยู่ใน
`UsersPage.test.tsx` ต้องเข้าถึงผ่าน:

```
UsersPage → mock api.get ให้ตอบ roster → QueryClientProvider → MemoryRouter → แล้วค่อยหาแถว
```

**หลังแยก** — `UsersTableRow.test.tsx` ยิง prop เดียว:

```tsx
render(
  <QueryClientProvider client={queryClient}>
    <Table><TableBody>
      <UsersTableRow user={user} />
    </TableBody></Table>
  </QueryClientProvider>,
);
```

ได้ 3 เคสที่ชื่อบอกตัวเองว่าทดสอบอะไร:

```
it("shows a live user with both actions")
it("badges a deleted user and offers nothing to do with them")
it("lets an admin be edited but not deleted")
```

(ยังต้องห่อด้วย `<Table><TableBody>` จริง เพราะ `<tr>` ลอยๆ เป็น DOM ที่ไม่ถูกต้อง และ
cell จะไม่มี role `cell` ถ้าไม่อยู่ในตาราง)

ตัวเลข `UsersPage` 139 → 99 บรรทัด และแถว 39 บรรทัด **เป็นผลพลอยได้ ไม่ใช่เหตุผล**

## 5. เหตุผลที่ฟังดูดี แต่ไม่ใช่เหตุผล

### ❌ "linter บอกว่า function ยาวเกิน"

**linter รายงาน ไม่ได้สั่ง** — `max-lines-per-function` ถูก**ปิดไปแล้วทั้ง 3 config**
(root, client, server) เพราะไม่เคยให้ finding ที่ควรทำตามเลย:

| ยิงตอนไหน | สิ่งที่ถูกต้องคือ |
|---|---|
| 106 บรรทัด บนฟอร์มที่มี **3 field** (แถมนับ comment ด้วย) | ไม่ทำอะไร — และมันเกือบถูกใช้เป็นข้ออ้างให้สร้าง `FormField` ที่ต้องถอนออก |
| 110 บรรทัด บน `UsersPage` ที่เป็น **logic ~25 บรรทัด ใต้ JSX ~85 บรรทัด** | ไม่ทำอะไร |

**ความยาวของ component ส่วนใหญ่คือ markup** → กฎนี้วัดผิดอย่างตั้งแต่ต้น

**`max-lines` (ทั้งไฟล์) เก็บไว้** — ยิง 1 ครั้ง บนไฟล์ spec ที่มี 3 verb ปนกัน และการแยกคือสิ่งที่ถูก

> การเก็บ warning ที่ house rule ประกาศไว้แล้วว่าจะไม่สนใจ มีผลเดียวคือสอนให้เราอ่านผ่าน
> lint output

### ❌ "มันลด code ที่ซ้ำกัน"

code ซ้ำคุ้มที่จะรวม **เฉพาะเมื่อมันต้องเปลี่ยนไปพร้อมกัน** · markup 5 บรรทัดซ้ำต่อ field
ที่แต่ละก้อนอ่านรู้เรื่องในตัวเอง ถูกกว่าการสร้างของที่คนอ่านต้องไปเรียนก่อน

### ❌ "เผื่อไว้ reuse ทีหลัง"

ส่วนใหญ่ไม่ได้ reuse และ prop ที่เดาไว้มักผิด (ดูข้อ 3)

### ❌ "มันคือ best practice"

ไม่มี practice ที่ตีพิมพ์ที่ไหนระบุจำนวนบรรทัดไว้ · default ที่ดีกว่าคือรูปร่างที่
**เอกสารของ library เขียนไว้**

### ❌ "ซอยให้ย่อยที่สุด"

ไล่ตามคำนี้จริงจะจบที่นี่:

```tsx
// ❌ ไม่มี state ไม่มี logic ไม่มีเงื่อนไข ไม่มีอะไรให้ test เล็ง
function EmailCell({ email }: { email: string }) {
  return <TableCell>{email}</TableCell>;
}
```

= JSX ชุดเดิมย้ายไปอยู่ที่ที่เปิดอ่านยากขึ้น · ช่อง email ไม่ใช่ข้อมูล 1 ชิ้น มันเป็น **คอลัมน์**
ของ `user` — เส้นแบ่งอยู่ที่ database มีอะไร ไม่ได้อยู่ที่เราซอยได้เล็กแค่ไหน

## 6. ประวัติการตัดสินใจในโปรเจกต์นี้ (เอาไว้เทียบ)

| ของ | ผล | เหตุผลที่ตัดสิน |
|---|---|---|
| **`FormField`** | **สร้างแล้วถอนออก** (2026-10-20) | ไม่ตรงกับข้อมูล + มีไฟล์ใช้เดียว · และ doc ของ shadcn ต่อ `id`/`htmlFor` ด้วยมือทุกตัวอย่าง = ไม่มีปัญหาให้แก้ |
| **`CreateUserDialog` + `CreateUserForm`** | **แยกไว้** | ฟอร์มถือ state ของตัวเอง · บวกข้อบังคับทาง technical: Radix unmount `DialogContent` ตอนปิด → `useForm` ที่อยู่ในลูกคือเหตุที่ทำให้ทุกครั้งที่เปิดได้ฟอร์มเปล่า |
| **`useCreateUser` / `useUpdateUser` → `features/users/api/`** | **ย้าย** (2026-10-23) | **ไม่ใช่** เพราะมีไฟล์ที่ 2 — แต่ละ hook ยังมีไฟล์ใช้เดียว · เหตุจริงคือกฎ folder structure + `UserRow` ติดอยู่ใน `pages/` ซึ่ง feature ห้าม import → ย้ายแล้วถึงใช้ `Pick<UserRow, …>` ได้ |
| **`UsersTableRow`** | **แยก** (2026-10-26) | 1 แถว = 1 user · การตัดสินใจครั้งแรกที่ยึด 2 ประโยคของ React เป็นหลัก · ผลตอบแทนอยู่ที่ test (ดูข้อ 4) |
