# Database index — มันคืออะไร และคุ้มเมื่อไหร่

## TL;DR (อ่านทวนเร็ว)

- **index = ข้อมูลอีกก้อน เก็บ 2 อย่างคู่กัน** — ① ค่าของคอลัมน์นั้น **เรียงแล้ว** ② **ตัวชี้ว่าอยู่แถวไหน** · ขาดอย่างใดอย่างหนึ่งแล้วใช้ไม่ได้ (ข้อ 2)
- **"เรียงแล้ว" คือตัวที่ทำให้ตัดครึ่งหาได้** → 100,000 แถว ใช้ราว **17 ก้าว** ไม่ใช่ 100,000 · และโตช้ามาก: 1,000,000,000 แถว ≈ 30 ก้าว (ข้อ 3)
- **เร็วเพราะ "รู้ตำแหน่งก่อนแตะแถวแรก"** — **ไม่ใช่** เพราะ "เจอแล้วหยุด" (ข้อ 4 มีเคสพิสูจน์ 2 เคส)
- **ช้าเพราะ** ทุก `INSERT` / `UPDATE` / `DELETE` ที่กระทบคอลัมน์นั้น ต้องไปแก้ index ด้วย (ไม่งั้นตัวชี้ผิด) + กิน disk
- **คุ้มเมื่อเงื่อนไข*ตัดแถวออกได้เยอะ*** ไม่ใช่แค่ "มี `WHERE`" — คอลัมน์ที่แถวส่วนใหญ่มีค่าเหมือนกัน index แทบไม่ช่วย
- **`@@unique` คือ index ด้วย** ไม่ใช่แค่กฎ — Postgres บังคับ "ห้ามซ้ำ" ได้เพราะมี index ไว้เช็ค
- **primary key (`@id`) มี index ให้อัตโนมัติ** → query ที่หาแถวด้วย `id` เร็วอยู่แล้ว ไม่ต้องทำอะไรเพิ่ม
- **ใส่ index ไม่ได้ทำให้อะไรถูกกรองออก** — ตัวที่เปลี่ยนพฤติกรรมคือ `where` ใน query, index แค่ทำให้เร็ว
- โปรเจกต์นี้ **ตั้งใจไม่ทำ index บน `User.deletedAt`** และเหตุผลอยู่ในข้อ 7

---

## 1. ไม่มี index → Postgres ต้องทำอะไร

```sql
SELECT * FROM "user" WHERE email = 'agent@example.com';
```

Postgres **ไม่มีทางรู้ว่าแถวนั้นอยู่ที่ไหน** → อ่านทุกแถวแล้วเทียบทีละแถว (sequential scan)

```
แถว 1: somebody@test.com    ไม่ตรง
แถว 2: admin@example.com    ไม่ตรง
แถว 3: agent@example.com    ✅ ตรง  ← ยังหยุดไม่ได้ อาจมีอีก
```

3 แถวไม่รู้สึกอะไร · **100,000 แถว = เทียบ 100,000 ครั้ง ทุกครั้งที่มีคน login**

หยุดก่อนครบได้ 2 กรณีเท่านั้น: มี `LIMIT` หรือคอลัมน์นั้น unique (ซึ่ง unique ก็มี index อยู่แล้ว)

## 2. index เก็บ 2 อย่าง และต้องมีคู่กัน

เป็น **โครงสร้างข้อมูลอีกชุด** ที่ Postgres สร้างและดูแลไว้ข้างๆ ตาราง

ของจริงจาก 3 แถวในโปรเจกต์นี้:

```
ตารางจริง "user"                    index บน email
(เรียงตามที่ insert เข้ามา)          (เรียง a→z)
──────────────────────              ─────────────────────────────
แถว 1  somebody@test.com            admin@example.com     → แถว 2
แถว 2  admin@example.com            agent@example.com     → แถว 3
แถว 3  agent@example.com            somebody@test.com     → แถว 1
            ▲                              ▲                  ▲
       ไม่ได้เรียง                   ① ค่าที่เรียงแล้ว    ② ตัวชี้ว่าอยู่แถวไหน
```

**"เรียงแล้ว"** = ค่าในคอลัมน์นั้นถูกจัดเรียง (a→z สำหรับตัวหนังสือ · น้อย→มาก สำหรับเลขและวันที่)
· **ตารางจริงไม่ได้เรียง index เรียง** นี่คือของ 2 ก้อนที่ต่างกันจริงๆ

### ขาดอย่างใดอย่างหนึ่ง = ใช้ไม่ได้

| มีแต่ตัวชี้ แต่ไม่เรียง | มีแต่เรียง แต่ไม่มีตัวชี้ |
|---|---|
| จะหาค่าใน index ก็ยังต้องไล่ดูทุกบรรทัดใน index → **ไม่ได้อะไรเลย** | รู้ว่ามีค่านี้อยู่ แต่ **ไปเอาข้อมูลจริงไม่ได้** |

- **"เรียง" = ตัวที่ทำให้ตัดครึ่งหาได้** (ข้อ 3)
- **"ตัวชี้" = ตัวที่ทำให้กระโดดไปแถวจริงได้**

## 3. "ตัดครึ่ง" — ที่มาของเลข 17

เพราะ index เรียงแล้ว Postgres จึง **ทิ้งของไปครึ่งหนึ่งต่อหนึ่งก้าว**

ของเล็กก่อน — index บน email 8 ค่า หา `gold@x.com`:

```
[ apple  bee  cat  dog  egg  fig  gold  hat ]      ← 8 ค่า

ก้าวที่ 1: ดูตรงกลาง = "egg"
           gold > egg  →  ทิ้งครึ่งซ้ายทั้งก้อน
           [ fig  gold  hat ]                       ← เหลือ 3

ก้าวที่ 2: ดูตรงกลาง = "gold"  →  เจอ ✅
```

**8 ค่า ใช้ 2-3 ก้าว ไม่ใช่ 8 ก้าว**

### 100,000 แถว ได้ 17 ก้าว

```
100,000 → 50,000 → 25,000 → 12,500 → 6,250 → 3,125 → 1,562 → 781 → 390
   → 195 → 97 → 48 → 24 → 12 → 6 → 3 → 1          = 17 ก้าว (log₂ 100,000)
```

### จุดที่น่าจำ — มันโตช้ามาก

| จำนวนแถว | ก้าว |
|---|---|
| 1,000 | 10 |
| 100,000 | 17 |
| **1,000,000** | **20** |
| **1,000,000,000** | **30** |

**แถวเพิ่มพันเท่า ก้าวเพิ่ม 10** — นี่คือเหตุผลทั้งหมดที่ index มีอยู่

*(ของจริง Postgres ใช้ B-tree ที่ตัดทิ้งได้มากกว่าครึ่งต่อก้าว เลขจริงจึงน้อยกว่า 17 อีก
หลักการเดียวกัน — ตัวเลขเป๊ะๆ ไม่สำคัญ สำคัญที่มันโตช้า)*

### เคส "ไม่เจอ" ก็เร็วเท่ากัน

`WHERE email = 'nobody@nowhere.com'` → ตัดครึ่งไป 17 ก้าวเหมือนกัน แล้วไปจบที่ช่องที่
**ควรจะมีค่านี้อยู่** แต่ไม่มี → **ตอบ "ไม่มี" ได้เลย**

เพราะมันเรียงอยู่ ถ้าค่านี้มีอยู่จริงมันต้องอยู่ช่องนั้น → ไม่อยู่ = ไม่มีจริง
**ไม่ต้องไปดูที่อื่นเพื่อยืนยัน**

## 4. ⚠️ เร็วเพราะ "รู้ตำแหน่งก่อนแตะแถวแรก" ไม่ใช่ "เจอแล้วหยุด"

นี่คือจุดที่เข้าใจผิดกันมากที่สุด เอาความเข้าใจ *"index ช่วยเพราะเจอแล้วไม่ต้องแตะที่เหลือ"*
ไปทาบ 2 เคสนี้ แล้วมันทำนายผิดทั้งคู่:

### 🧪 เคส 1 · แถวที่ตรงอยู่ท้ายสุด (แถวที่ 100,000)

| | "เจอแล้วหยุด" ทำนายว่า | ของจริง |
|---|---|---|
| ไม่มี index | แตะ 100,000 แถว | แตะ 100,000 ✅ |
| **มี index** | เจอที่แถวสุดท้าย → ก็ต้องแตะ 100,000 อยู่ดี → **index ไม่ช่วยเลย** | **~17 ก้าว** ❌ ไม่ตรง |

### 🧪 เคส 2 · query ที่ไม่เจออะไรเลย

| | "เจอแล้วหยุด" ทำนายว่า | ของจริง |
|---|---|---|
| ไม่มี index | แตะ 100,000 แถว | แตะ 100,000 ✅ |
| **มี index** | ไม่เคยเจอ → ไม่มีจุดให้หยุด → แตะ 100,000 อยู่ดี | **~17 ก้าว** ❌ ไม่ตรง |

### กลไกจริง

```
ไม่มี index:  "ไม่รู้ว่าอยู่ไหน"   →  ต้องเดินดูทุกแถว แล้วค่อยรู้
มี index:     "อยู่ตำแหน่งนี้"     →  เดินตรงไปเลย ไม่ได้ "เดินแล้วหยุด"
                                       ถ้าไม่มี มันก็รู้ว่าไม่มี โดยไม่ต้องเดิน
```

**ความต่างคือ "เดินแล้วหยุดเร็ว" กับ "ไม่เดินเลย"**

เรื่อง "ไม่มี index แล้วเจอแล้วยังต้องเดินต่อจนจบ" **เป็นเรื่องจริง** แต่มันเป็น **อาการ**
ของการไม่รู้ตำแหน่ง ไม่ใช่ **สาเหตุ** ที่ index เร็ว

**ทำไมต้องแยกให้ออก:** ถ้ายึดว่า "เจอแล้วหยุด" จะสรุปผิดว่า index ช่วยทุก query ที่มี `WHERE`
ซึ่งเป็นที่มาของข้อ 6

## 5. ราคาที่จ่าย

| ราคา | เพราะอะไร |
|---|---|
| **พื้นที่ disk** | เป็นข้อมูลอีกชุดจริงๆ |
| **ทุก `INSERT` / `UPDATE` / `DELETE` ช้าลง** | เขียนแถวแล้วต้องไปแก้ index ด้วย ไม่งั้นตัวชี้ชี้ผิด |

**index = แลกความเร็วตอนอ่านแบบกรอง ด้วยความเร็วตอนเขียน**

---

## 6. คุ้มเมื่อไหร่ — **เงื่อนไขต้องตัดแถวออกได้เยอะ**

```
สมมติ 100,000 แถว  ·  ถูกลบไป 20 แถว

WHERE deletedAt IS NOT NULL  → ตรง 20 แถว      ✅ index ช่วยมาก
WHERE deletedAt IS NULL      → ตรง 99,980 แถว  ❌ index ไม่ช่วย
```

กรณีล่าง Postgres ต้องไปแตะเกือบทุกแถวอยู่ดี → **อ่านทั้งตารางตรงๆ เร็วกว่า** และ optimizer
ก็จะเลือกไม่ใช้ index เอง

**"มีการกรอง" ไม่เท่ากับ "ควรมี index"**

## 7. ของจริงในโปรเจกต์นี้

### index ที่มี และเหตุผลของแต่ละอัน

| ที่ไหน | index | ใครใช้ |
|---|---|---|
| [schema.prisma:119](../../server/prisma/schema.prisma#L119) | `@@unique([email])` บน `User` | `/sign-in/email` หา user จาก email ทุกครั้งที่ login |
| [schema.prisma:134](../../server/prisma/schema.prisma#L134) | `@@unique([token])` บน `Session` | better-auth อ่าน session จาก token ใน cookie **ทุก request** |
| [schema.prisma:135](../../server/prisma/schema.prisma#L135) | `@@index([userId])` บน `Session` | `session.deleteMany({ where: { userId } })` ใน [delete-user.ts:56](../../server/src/users/delete-user.ts#L56) |
| [schema.prisma:155](../../server/prisma/schema.prisma#L155) | `@@index([userId])` บน `Account` | `update-user.ts` อ่าน account row ของ user |
| ทุก model | `id @id` | primary key — **Postgres สร้าง index ให้อัตโนมัติ** |

**`@@unique` คือ index ด้วย** นั่นคือเหตุที่ทางเลือกของเรื่อง email ถูกเรียกว่า
**"partial unique index"** ไม่ใช่ "partial unique rule"

### ทำไม `User.deletedAt` **ตั้งใจไม่ทำ index**

หลักเดียว: **index ช่วยเฉพาะเมื่อ query ใช้คอลัมน์นั้น "หา" แถว**

ทั้งโปรเจกต์มี 4 ที่ที่แตะ `deletedAt`:

| ที่ | code | ใช้ `deletedAt` หาแถวไหม |
|---|---|---|
| `GET /api/users` [users.routes.ts:37-40](../../server/src/users/users.routes.ts#L37-L40) | `findMany({ select, orderBy })` — **ไม่มี `where` เลย** | ❌ อ่านทุกแถวโดยตั้งใจ เพราะตารางต้องโชว์คนที่ถูกลบแบบจาง → ไม่มีอะไรให้ตัดทิ้ง |
| `softDeleteUser` [delete-user.ts:42](../../server/src/users/delete-user.ts#L42) | `where: { id, role: { not: "admin" }, deletedAt: null }` | ❌ หาแถวด้วย `id` (primary key มี index แล้ว) → ได้แถวเดียว แล้วเช็ค 2 คอลัมน์บนแถวนั้น ซึ่งไม่มีราคา |
| `updateUser` [update-user.ts:49](../../server/src/users/update-user.ts#L49) | `where: { id, deletedAt: null }` | ❌ เหมือนข้างบน |
| `auth.ts` hooks | `findUnique({ where: { email } })` แล้วอ่าน `deletedAt` | ❌ หาด้วย email index |

**ทุกที่ไปถึงแถวด้วย `id` หรือ `email` ที่มี index อยู่แล้ว ไม่มีที่ไหนใช้ `deletedAt` เป็นตัวหา**

→ ใส่ index ไป = จ่ายค่า disk + ทำให้ทุก delete และทุก seed ช้าลง **โดยไม่มี query ไหนได้ประโยชน์**
และถึงวันที่มีคนกรอง `WHERE deletedAt IS NULL` จริง ก็ยังเข้าเคสข้อ 6 ที่ index ไม่ช่วย

comment ที่ [schema.prisma:105-106](../../server/prisma/schema.prisma#L105-L106) เขียนไว้ว่า
*"Add one only if a query starts filtering"* — มีไว้กันคนมาเพิ่มให้เอง เพราะคนที่เห็นคอลัมน์
soft delete ไม่มี index จะคิดว่าลืม

### ถ้าวันหนึ่งอยากให้ `GET /api/users` กรองคนที่ถูกลบออก

```
① แก้ query ให้กรอง:   findMany({ where: { deletedAt: null }, ... })   ← ตัวที่เปลี่ยนพฤติกรรม
② วัดว่าช้าจริงไหม
③ ถ้าช้า → schema เพิ่ม @@index([deletedAt]) + migrate                ← ตัวที่ทำให้เร็ว
```

**ใส่ index เฉยๆ ไม่ทำให้อะไรถูกกรองออก** และข้ามข้อ ② ไปเลยก็มีสิทธิ์ได้ index ที่ไม่มีใครใช้

### มี query ที่ "กรอง" แล้วจริง — และยังไม่ใส่ index

webhook ที่รับ email มี query กัน ticket ซ้ำ ที่
[inbound-email.routes.ts](../../server/src/tickets/inbound-email.routes.ts) หาด้วย
`where: { senderEmail, status: "open", subject }` — ครั้งแรกที่โปรเจกต์นี้มี query ใช้คอลัมน์
ที่ไม่มี index เป็นตัว "หา" แถว เพราะงั้นตัวอักษรของ comment ที่ `User.deletedAt`
(*"Add one only if a query starts filtering"*) เข้าเงื่อนไขแล้ว — **แต่เหตุผลของมันยังไม่เข้า**
และความต่างนั้นคือหัวใจข้อ 6:

| คอลัมน์ | ตัดแถวออกได้แค่ไหน | คุ้มไหม |
|---|---|---|
| `status` | 3 ค่า และเกือบทุกแถวเป็น `open` | ❌ ตรงเกือบทั้งตาราง — เคสล่างของข้อ 6 เป๊ะ |
| `category` | 3 ค่า (ยังไม่มี query ไหนกรองเลย) | ❌ |
| `senderEmail` | แทบจะ unique ต่อคน | ✅ **ตัวนี้คือตัวแรกที่ควรได้ index** — แต่รอข้อ ② |

ตอนนี้ `ticket` มีหลักสิบแถว อ่านทั้งตารางเร็วกว่าอยู่แล้ว → รอให้ `EXPLAIN` บอกว่า seq scan
กินเวลาจริงก่อน แล้วค่อยใส่ `@@index([senderEmail])`

**บทเรียนที่เพิ่มมาจากรอบนี้:** comment ในโค้ดที่เขียนว่า "ใส่เมื่อมีการกรอง" สั้นเกินไปหนึ่งขั้น
เกณฑ์ที่ใช้จริงคือ "กรองแล้วตัดแถวออกได้เยอะหรือเปล่า" ไม่ใช่ "มีการกรองหรือยัง"

## 8. 3 จุดที่เข้าใจผิดบ่อย

| ❌ ที่คิด | ✅ ที่เป็น |
|---|---|
| "เร็วเพราะเจอแล้วหยุด" | เร็วเพราะ **รู้ตำแหน่งก่อนแตะแถวแรก** · ดูเคสพิสูจน์ 2 เคสในข้อ 4 |
| "เก็บแค่ค่าที่เรียงแล้วก็พอ" | ต้องมี **ตัวชี้ว่าอยู่แถวไหน** คู่กัน ไม่งั้นไปเอาข้อมูลจริงไม่ได้ (ข้อ 2) |
| "index table" | ไม่ใช่ table — `SELECT` ตรงๆ ไม่ได้ ไม่มีชื่อให้เรียก เป็น **โครงสร้างแยกที่ Postgres ดูแลเอง** เรียก "index" เฉยๆ |

`server/prisma/schema.prisma` คือ **แหล่งความจริงหนึ่งเดียว** ว่า data หน้าตายังไง
แต่มันไม่ sync เอง — **เป็น 2 คำสั่งแยกกัน และเดินไม่พร้อมกันได้**

            ┌───────────────┴───────────────┐
            ▼                               ▼
   npm run db:migrate              npm run db:generate

   prisma/migrations/              server/src/generated/prisma/
   แล้วรันใส่ Postgres              (ปลายทางกำหนดใน generator block)
